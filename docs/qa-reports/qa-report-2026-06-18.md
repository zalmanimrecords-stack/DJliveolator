# Liveolator QA report — 2026-06-18 (full-app sweep)

## Verdict

The app is **buildable and the test suite is fully green** at the state I finished
against (`2212 pass / 0 fail / 2 skip`, clean build). It is **not currently shippable**
because the branch `feat/studio-tab` is under live edit and I caught it in a
**non-compiling working-tree state at the start of the sweep** — 9 `CS0103` errors in
`WaveformStrip.cs` (missing `StyledProperty` declarations for `PlayheadBrush` /
`BeatBrush` / `DownbeatBrush`). The active developer fixed it mid-sweep, but a branch
that does not compile on checkout is the single worst risk here: it means commits are
landing without a green `run.ps1 -BuildOnly` gate.

The most important *logic* defect is a proven **wrong-result bug in the STUDIO offline
mixdown**: the per-clip fade/gain envelope (`ClipGain`) anchors on the *un-warped* clip
end while the render plan (`MixPlan`) selects the active clip on the *warped* end. For a
warped clip with a fade-out this produces either a multi-second **silent tail** (warp
down) or a **missing fade-out** (warp up) in the exported WAV. It is proven by two
failing xUnit tests. It is **not reachable from the UI today** (no per-clip gain/fade
editor exists yet) — it is a latent correctness bug in built-but-not-wired code that
will bite the moment the fade UI lands.

## Critical / High defects

### H1 · High · STUDIO offline render · Warped clip fade-out is computed against the wrong clip end → silent tail / missing fade in the exported mix

- **✅ FIXED 2026-06-18.** `ClipGain.EffectiveGainAt` now takes an optional `effectiveEndSeconds`
  and `MixPlan` passes the clip's **warped** end, so the fade-out and silence cutoff anchor on the
  same end the active-clip selection uses. The two repro tests now pass (regression guards). The live
  path (`StudioArranger`) was left unchanged — it is warp-agnostic and self-consistent, so the fix is
  confined to the render side as recommended.
- **Symptom (two faces of one root cause):**
  1. *Warp down (slower/longer):* a 120-BPM, 60 s source warped to a 100-BPM project has a
     warped timeline end of `60 / (100/120) = 72 s`. `MixPlan.ActiveClip` keeps the clip
     active to 72 s, but `ClipGain.EffectiveGainAt` returns **0 from 60 s onward** (the
     un-warped `TimelineEndSeconds`). Result: the tail `[60 s, 72 s)` is selected-as-audio
     but **silent** — a 12-second dropout in the rendered WAV.
  2. *Warp up (faster/shorter):* warped end ≈ 51.43 s, but the 4 s fade-out anchors on the
     un-warped 60 s end, so just before the real audible end the gain is still **~full**
     instead of ~0 — the requested fade-out **never happens** in the render.
- **Repro (failing xUnit):**
  `tests/Liveolator.Core.Tests/Studio/MixPlanWarpedFadeReproTests.cs`
  - `Repro_WarpedClipTail_GoesSilentBeforeItsWarpedEnd`
  - `Repro_WarpedUpClip_FadeOutDoesNotReachZeroAtItsAudibleEnd`
- **Evidence (actual failing assertions):**
  ```
  Failed ...Repro_WarpedClipTail_GoesSilentBeforeItsWarpedEnd
    Assert.Equal() Failure: Values are not within tolerance 1E-09
    Expected: 1   (Actual gain at t=65s was 0)
  Failed ...Repro_WarpedUpClip_FadeOutDoesNotReachZeroAtItsAudibleEnd
    expected the fade-out to be near 0 at the warped clip end, but gain was 1
  ```
- **Root cause @ file:line:**
  - `src/Liveolator.Core/Studio/ClipGain.cs:30-31` (silence cutoff on `end` = `clip.TimelineEndSeconds`)
    and `ClipGain.cs:51-58` (`FadeOutFactor` anchors `remaining = e - t` on the same un-warped `end`).
  - `clip.TimelineEndSeconds` is **un-warped**: `src/Liveolator.Core/Studio/StudioClip.cs:35-36`
    (`TimelineStartSeconds + SourceDuration`, no warp factor).
  - `src/Liveolator.Core/Studio/Render/MixPlan.cs:82` + `93-96` select the active clip on the
    **warped** end (`start + WarpMath.WarpedTimelineSeconds(d, factor)`). The two ends disagree
    for any warped clip.
  - Propagation to audio: `src/Liveolator.Audio/Render/OfflineMixRenderer.cs:103,123,126`
    multiplies `state.Gain` straight into the rendered samples.
- **Reachability caveat:** **Not reachable from the UI today** — the STUDIO UI never sets
  `StudioClip.Gain`, `FadeInSeconds`, or `FadeOutSeconds` (clips are created at unity/no-fade;
  see `src/Liveolator.App/Features/Studio/StudioViewModel.cs:399-401`, and
  `StudioClipViewModel.cs` exposes no gain/fade editor). This is a latent bug in the
  per-clip-gain/fade model + render path that shipped ahead of its editor.
- **Suggested fix (owner-scheduled, not done here):** make `ClipGain.EffectiveGainAt` take the
  *effective (warped) timeline end* — pass the warped end down from `MixPlan` (and `StudioArranger`),
  or give `ClipGain` a warp-aware end parameter — so the fade-out and the silence cutoff use the
  same clip end the active-clip selection uses. The live-playback path (`StudioArranger`, which
  explicitly does not model warp — `StudioArranger.cs:121-124`) stays self-consistent, so the fix
  is confined to the render side.

### L2 · Low · STUDIO live playback · A per-clip gain *boost* (`Gain > 1.0`) with no gain lane is silently not emitted

- **Symptom:** `StudioArranger.AutomationActionsAt` only emits a `MixerChannelGain` action for a
  laneless clip when `envelope < 1.0`. A clip with `Gain = 1.5` and no fades has `envelope = 1.5`,
  which fails the `< 1.0` guard, so **no gain action is emitted** and the boost is never heard in
  live playback. This contradicts the method's own doc ("A deck with a per-clip gain/fade but no
  gain lane still emits a gain action so the fade is heard").
- **Root cause @ file:line:** `src/Liveolator.Core/Studio/StudioArranger.cs:86` (the `envelope < UnityGain`
  guard) combined with `StudioClip.Gain` being an unclamped `double` (`StudioClip.cs:24`).
- **Why only Low:** A boost can never be honored anywhere downstream regardless — every gain sink
  clamps to `[0,1]` (`MixPlan.cs:45,60`; `MixerActionHandler` channel-gain clamp). And `Gain > 1.0`
  is **not reachable from the UI** today. So this is a latent contract inconsistency, not live-set
  harm. (Verified the rest of the gain/clamp paths are consistent.)

## Could not reproduce (hypotheses)

- **`int` overflow on very long renders.** `OfflineMixRenderer.RenderAsync:72,89` casts
  `Math.Ceiling(DurationSeconds * sampleRate)` to `int` and allocates `new float[totalSamples * 2]`.
  `totalSamples * OutputChannels` overflows `int` at roughly a ~3.4-hour stereo render at 44.1 kHz.
  I did not write a repro — a multi-hour single-project render is implausible for a DJ set and the
  failure mode (allocation throw / negative size) would be loud, not silent. Flagged as an
  unconfirmed robustness edge; a `long`/checked-size guard would remove it.
- **Runtime/UI sweep of LIVE/DJ/VJ/LIBRARIES/MAPPINGS/SETTINGS.** I could not exercise the GUI
  (no click access) and the app log was not consulted for a live run because the build was red for
  the first part of the sweep and the branch was actively changing under me. The Core logic behind
  these surfaces (mixer math, beat clock/quantizer, automation interpolation, transport, crossfader
  laws, cue mix) was statically swept and came back **clean** — see below — but I did not observe
  them running. This is a coverage gap, not a clean bill of health for the running UI.

## Coverage notes (swept, no solid defect found)

Pure-logic review (with a focused subagent) of the audio/sync core came back clean against each
type's documented contract: `MixerMath` (crossfader laws at p=0/1, EQ kill/unity, filter-center
bypass, `Omega` frequency clamp — no divide-by-zero), `MixerState`/`DeckChannelState`/`EqBands`/
`CueMixMath` (all clamp inputs; equal-power blend correct at 0/1), `BeatTimeline` (rejects bpm≤0/NaN,
floored modulo handles negative/pre-anchor time, on-boundary resolves to "now"), `BeatQuantizer`/
`Quantize` (guards `everyN<1`, `beatsPerBar≤0`), `AutomationLane.ValueAt` / `TempoCurve.TempoAt`
(boundary scan in range, coincident-keyframe guard, early-return prevents the last-index off-by-one),
and `StudioTransport` (half-open `[from,to)` windows consistent, seek clamps ≥0, monotonic dispatch
cursor).
